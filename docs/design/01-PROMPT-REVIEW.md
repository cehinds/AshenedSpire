# 01 — Review of the original rebuild mega prompt

Source reviewed: `ASHEN-SPIRE-REBUILD-MEGA-PROMPT.md`, the browser-first clean-room rebuild prompt.
It was checked against the shipped game in `D:\repos\AshenSpire`, the earlier Unity port in `D:\repos\AshenSpire-Unity`, and the tooling on this machine.

The rules content of the original prompt is strong. Most of its problems are about **delivery**: which platform, how the session runs, and how "no hard-coding" is enforced. The new prompt ([09-UNITY-MEGA-PROMPT.md](09-UNITY-MEGA-PROMPT.md)) keeps the rules and changes the delivery.

## B. Problems and the improvement made

### B1. Platform and session model

| # | Problem in the original | Improvement |
|---|---|---|
| 1 | The target is a `<TARGET>` placeholder, and the web build is the default. The owner now wants **Unity**. | Unity 6 is the only target. The prompt pins the render pipeline (URP 2D), UI (UI Toolkit), input (Input System) and packages. |
| 2 | "Stop at the review gate" and "Wait for approval before M1" contradict the new requirement of **one session with no human input**. | Human gates become **self-gates**: automated checks, MCP screenshots, and a sub-agent review with a written verdict. Blocking questions go to `DECISIONS.md` with a provisional default. The session never stops to ask. |
| 3 | Web-only tooling: Vite, Playwright, a single-file build, a mobile HTML under 30 MB, and a Node LAN server. | Unity equivalents: Unity Test Framework (EditMode and PlayMode), an in-editor headless bot, MCP screenshot capture, a Windows standalone build, and optional Android/WebGL profiles with per-platform size budgets. |
| 4 | Co-op (M5) needs a WebSocket server, which is a large, separate project. | Co-op is **out of scope** for the one-session build. Only its seams ship: seat-indexed player state and commands as serializable intents. See the scope doc. |
| 5 | Nothing about how the session should use the Unity MCP, Blender or sub-agents. | A tool contract: what the Unity MCP is used for (create assets and scenes, run tests, read the console, take screenshots), what Blender may do (re-export and composition only), and when to fan out sub-agents. |

### B2. Unity-specific traps the original never mentions

| # | Trap | Improvement |
|---|---|---|
| 6 | **Unity cannot import `.webp`.** Almost every image in the asset set is WebP. | Step 1 of the pipeline converts WebP to lossless PNG. It uses **Blender 4.0 headless**, which reads and writes WebP and is already installed; `pip install pillow` is the second choice. Allowed under "re-export / recompress". Output goes to a generated import folder that is never hand-edited. |
| 7 | **SVG** (the parchment maps, `missing.svg`, the tower-door masks) needs `com.unity.vectorgraphics` or rasterizing. | Rasterize SVGs to PNG at 2× the reference size during import. Record the choice in `DECISIONS.md`. |
| 8 | Fonts need TextCore Font Assets for UI Toolkit. | Font assets are generated by an editor script from `fonts.json` (font id → file, weights, roles). No font is referenced by path. |
| 9 | About 3,000 animation frames as loose sprites cost draw calls and memory. | A Sprite Atlas per suite and outfit, built by script. Frame order comes from the numeric suffixes. Loading is lazy: the equipped suite only, through Addressables labels. |
| 10 | Determinism: `UnityEngine.Random`, `float` maths and `Dictionary` iteration order all break replays. | The domain assembly has `noEngineReferences: true` and uses integer or fixed-point maths, a custom PRNG with named streams, and ordered collections. A test fails if domain code references `UnityEngine`. |
| 11 | Saves: the web used localStorage with a mirror. | `Application.persistentDataPath`, atomic write (temp file → fsync → replace), a verified mirror copy, and a schema version with migrations. |
| 12 | JSON-schema validation in C#: Newtonsoft.Json.Schema is AGPL/commercial. | Use `com.unity.nuget.newtonsoft-json` for parsing, plus an in-house validator driven by `*.schema.json` descriptors. No AGPL dependencies. |

### B3. "No magic strings, no hard-coding" is stated as a wish, not enforced

| # | Problem | Improvement |
|---|---|---|
| 13 | Nothing prevents `if (status.id == "bleed")` or `"Continue"` in C#. | **Enforced conventions:** content IDs live only in data. Code reads *roles* through config keys (for example `balance.run.startingCinders`). Codegen emits typed key constants for **schema keys only**, never for content IDs. An EditMode test scans `Domain/` and `Application/` for string literals outside an allowlist and fails the build. |
| 14 | UI text is not covered. | Every user-facing string lives in a string table (`strings/en.json`, keyed). Card text uses templates filled from the same preview functions the engine uses. |
| 15 | The effect DSL is mentioned but never defined. | The new prompt specifies the op vocabulary (`damage`, `block`, `applyStatus`, `draw`, `gainResource`, `enterStance`, `forEachTarget`, `if`, `repeat`, and more), the trigger vocabulary and the target selectors. All are registered by op name from data, with a validator. |
| 16 | The config layering is unclear. Advanced settings, Custom Run and balance all touch the same numbers. | An explicit stack: `defaults → balance → difficulty/ascension → customRun modifiers → advanced settings → per-run snapshot`. Each layer is a JSON patch validated against the same schema, and the snapshot is frozen into the save. |

### B4. Internal ambiguities in the rules text

| # | Ambiguity | Resolution |
|---|---|---|
| 17 | "Poise" means three things: the meter, the rating, and the resistance R. | Distinct names: `poiseMeter` (fills to break), `poiseRating` (resistance input), `poiseResist` (derived multiplier). The same split applies to Ward. |
| 18 | The Actions/turn row says only "small attribute terms". | Import the weights from `derivedStats` data. Never re-type them. |
| 19 | "Brace" is both a stance and a taken-multiplier. | One status definition with a `damageTakenMultiplier` field, granted by the Brace stance's `onEnter`. |
| 20 | The title menu lists 7 entries plus 4 missing ones, too many for one column. | Keep the owner's order and fold the missing entries in: Continue · Load · New · Journal (Collection / History / Profile) · Custom Run · Settings (About holds the credits and AI disclosure) · Quit. LAN is hidden while co-op is out of scope. "Offline / Download & saves" is dropped because it was web-only; save import/export moves to Settings. |
| 21 | Resuming mid-combat means serializing the whole combat state. | Save a **snapshot + command log**. A resume replays the commands from the last committed snapshot, and the golden replays exercise the same path. |
| 22 | Build steps are defined per milestone, but there is no **order of building inside** a milestone. | Component by component: each component goes data schema → domain → tests → view-model → UXML wireframe (grey box) → skin with real assets → screenshot review. The wireframes in [04-WIREFRAMES.md](04-WIREFRAMES.md) are the build blueprint. |
| 23 | No plan for running out of context or time in one session. | A **scope-cut ladder**: which features drop first, and a rule that `main` is always playable after every component. |

### B5. Missing artefacts

The original has no scope doc, feature list, user stories, wireframes or flow diagrams. Without them an unattended session tends to invent screens and flows. This package adds:

- [02-SCOPE.md](02-SCOPE.md): in, out, and seams only.
- [03-FEATURES-AND-USER-STORIES.md](03-FEATURES-AND-USER-STORIES.md): an epic → feature → story list with acceptance criteria.
- [04-WIREFRAMES.md](04-WIREFRAMES.md): every screen at 1280×720, plus portrait rules and component IDs.
- [05-ACTIVITY-FLOWS.md](05-ACTIVITY-FLOWS.md): what the player does.
- [06-PROCESS-FLOWS.md](06-PROCESS-FLOWS.md): what the system does, covering boot, save, content load, combat resolution and the asset pipeline.
- [07-DIAGRAM-REVIEW.md](07-DIAGRAM-REVIEW.md): the sub-agent review of the diagrams and how each finding was resolved.
- [08-DATA-CONVENTIONS.md](08-DATA-CONVENTIONS.md): IDs, schemas, config layers, the effect DSL, and the no-magic-strings rules.

### C4. UI conventions the original omitted (from the shipped wireframe atlas)

- **Authority:** `docs/architecture-handoff/CURRENT-SPECIFICATION.md` comes first, then `RESPONSIVE-WIREFRAMES.md` (Wide, Compact, iPhone SE, Galaxy S24) and `implementation/approved-wireframes.md` (dated owner decisions).
- **Shell W0:** title top-left, exit top-right, Back bottom-left, Primary bottom-right. Labels never wrap.
- **Rule 11:** multi-category screens use a **rail** on wide layouts and a `[Category ▾]` selector on compact ones. **No horizontal tabs, no accordions.**
- **Height bands:** ≥465 px is standard; 340–464 px is compact short-wide ("rails"); under 340 px shows the upright gate.
- **Combat bands:** 10/55/30/5, hand ≥208 px, footer ≥56 px. The footer is one centred group: (Actions)[Draw][End Turn][Discard/Exhaust](Potions), with a **64 px pile floor**. The top HUD never shows potions.
- **Map:** select, then Enter. A repeat pick travels only after **400 ms**. The node tray opens after 150 ms.
- **Selection and inspection:** one gold glow. The Inspect (i) control appears after 1,000 ms. On touch, the first tap selects and the second explains.
- **Colours:** Exit and Back turn red on focus; a ready primary is green; neutral is brown and gold; disabled overrides everything.
- **Buttons:** 9 sizes ({third, half, full} × {standard, tall, double}). Standard height is 44 px.
- **Credits and the AI disclosure** live under **Settings → About**. There is no separate credits screen.
- The victory and defeat headlines are "EMBER RESTORED" and "YOU PERISHED".

[04-WIREFRAMES](04-WIREFRAMES.md) follows these conventions.

### C5. The previous Unity attempt (`D:\repos\AshenSpire-Unity`)

- **Editor:** Unity **6000.6.0f1** is installed at `D:\Unity\6000.6.0f1\Editor\Unity.exe` and was used by the old port. Blender **4.0** is at `C:\Program Files\Blender Foundation\Blender 4.0`.
- **What it built:** a simplified "adaptation" campaign (25 cards, 8 ops) plus engine-free C# ports of the RNG, formulas, map generator, statuses and damage order. They were checked against the JS through a **parity oracle** (`tools/unity-parity-import.mjs` → `reference.json`). Original combat orchestration was never finished.
- **Weaknesses:** content through `Resources` and `JsonUtility`, op names hard-coded in arrays, no Test Framework (.NET console harnesses instead), no Input System, no atlases, saves in `PlayerPrefs`.
- **Lessons to carry forward:**
  1. The **UI Toolkit WebGL renderer bug on 6000.6.0f1** (`CopyBufferRanges`) → Windows first, WebGL last.
  2. **Reuse the parity-oracle idea:** generate expected values from the JS for the formula and damage tests.
  3. **Governance:** automated messages once claimed owner approval falsely → the new session **never claims approval**. It works on a feature branch and opens a draft PR to `dev`.
- **Tooling:** no Unity MCP bridge or Blender MCP is configured on this machine yet. The mega prompt includes a preflight that installs and verifies one, and falls back to batchmode CLI.
